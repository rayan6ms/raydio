The server formerly replaced the paced Oto source even for gain/filter controls.
Replacement cancels the old producer and can discard an in-flight frame.
Controls now keep the same source and generation; actual transport/timeline
changes still replace it. A regression checks frame sequence, effective volume,
unchanged source ownership, and delivery of natural EOF after controls.

The Mantle adapter formerly rebuilt the filter pipeline for identical settings,
resetting decoder/encoder/DSP state. It now skips redundant committed settings.
It checks pending changes before taking the immediate path, so an accepted
change followed by restoration is not accidentally elided or reordered.

## Source audio evidence

The `source_packets --staged --repeat --redundant-filters` audit plays one
retained compressed input twice at volume 70. The first play has no intervening
controls; the second restates volume 70 every 100 frames (106 times). This is
an accelerated source audit, with approximately 23–25 seconds wall time per
213.06 seconds of generated audio. It does not connect to Discord.

Before, 8,238 packets differ between these two plays. After, every packet is
identical, including the same digest as the baseline play without controls.
There are no added/missing frames. Independent system-libopus decoding reports
zero near-full-scale/nonfinite samples, malformed frame durations or mid-track
quiet intervals >=20 ms in all four plays. The source tail remains 938.4375 ms.
Only aggregate diagnostics and hashes are committed; encoded audio stays in
ignored local artifacts.

Total time awaiting 106 controls was 19.295 ms before and 8.255 ms after. These
are single unoptimized runs with overlapping local compilation and scheduling
variation, so they are **not** a controlled latency/CPU benchmark. No new bot
memory saving, live button-latency reduction or delivery-loss reduction is
claimed. The proven improvements are unnecessary source replacement removal,
non-blocking redundant updates, and preservation of unchanged audio output.

## Correction to the earlier interpretation

Calling the entire recurring ~976 ms receiver tail a confirmed application bug
was incorrect. Existing independent Oracle source decoding already measured
938.458 ms of ending silence. The new source audit confirms it. Timing alignment
with a track restart does not establish the precise artificial handoff delay;
we did not trim the source, crossfade it, or implement speculative early looping.

The 14.184-second receiver outage and shorter delivery bursts still need an
independent receiver/network-path comparison. Sender counters from the six-hour
run do not justify codec, bitrate, pacer or encryption changes. Removing the
unchanged-filter reset is useful independently; it is not a claimed explanation
for those historical outages.

## Diagnostic reliability improvements

- The previously fixed checkpoint timer remains armed after failed preflights
  and retries failed writes.
- Local CPU/pressure/uptime/interface/UDP samples now run independently once per
  minute, even when the browser sends nothing. A real 65-second loopback smoke
  retained two valid host samples, 60.354 seconds apart, with no browser writes
  during the second sample. Delays are reported; missing time is not fabricated.
- The same persistence path accepts short trials and six-hour reports. Each
  observation uses a new directory, preventing accidental evidence replacement.
- `raydioCheckpoint.verify()` requires the actual running report to be saved,
  two independent host samples, and enough lifetime in both collectors for the
  rest of the observation plus a minute. Tests reject an old preflight's report,
  insufficient lifetime, missing samples and a stopped timer.
- The receiver retains 256 diagnostic windows instead of 128. That would have
  retained all 168 windows generated by the previous six-hour observation.
  Truncation accounting remains explicit under larger workloads.

If the previous timer had worked, the local host samples could have helped
correlate a receiver interruption with local resource pressure or UDP errors.
They would not necessarily identify a new bot fix, pinpoint the failing network
hop, or replace subsecond timing evidence. The missing history is unavailable.
